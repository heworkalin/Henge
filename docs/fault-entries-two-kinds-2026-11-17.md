# 缺页横跨两类完全不同的 entry —— 指向共同的底层

## 1. 实测（runS7，pid 31216，fault 20091 次时采样）

用 fault 自带的 ttbr0 精确匹配后，读每条 entry 的 `+0x40`（object union）与 `+0x48`（alias|offset）：

| entry | 页数 | `+0x40` | 判定 | `+0x48` |
|---|---|---|---|---|
| `[0x10a9cc000, 0x10aa50000)` | 33 | **0** | 匿名/内核对象（零填充） | `0x2002bac0` |
| `[0x105100000, 0x10519c000)` | 39 | **0** | 同上 | `0x2002aac0` |
| `[0x1052f8000, 0x105308000)` | 4 | **0** | 同上 | `0x2002bac0` |
| `[0x105440000, 0x1054dc000)` | 39 | **0** | 同上 | `0x2002aac0` |
| `[0x16a8d4000, 0x16b0d0000)` | 511 | **0x1e** | **子映射**（`is_sub_map=2`），线程栈 | `0x2b980` |
| `[0x16b640000, 0x16b6c8000)` | 34 | **0x1e** | 同上 | `0x2b980` |

（`0x40` 的位域：`vme_ctx_atomic:1`、`vme_ctx_is_sub_map:1`、`vme_context:30`；
`0x1e = 0b11110` → `is_sub_map=1`、`context=7`。）

## 2. 为什么这个结果重要

这两类 entry 在缺页处理里走的是**完全不同的代码路径**：

| 类别 | 缺页时内核要做什么 |
|---|---|
| `object = 0`（匿名/内核对象） | 分配一个新页、**清零**、装进 pmap（零填充路径） |
| `is_sub_map = 1`（子映射，这里是线程栈） | 进入子映射的 vm_map 继续查找，找到后由子映射的 object 走上面那条路 |

**两条路径都失败了，而且都表现成"PTE 不存在"。**

如果问题出在某一条路径内部（比如零填充逻辑、或子映射的查找），
**另一条不应该同时坏**。两条都坏说明故障点在它们的**共同下游**：

```
vm_fault_enter
   ├── 匿名零填充分支  ─┐
   └── 子映射分支      ─┤
                        ↓
                   pmap_enter        ← 共同下游
                        ↓
                   页表项被写入
```

## 3. 因此下一步很明确

**不再需要分别研究"零页路径"和"子映射路径"** —— 那两条看起来都是好的。

需要验证的是 `pmap_enter` 有没有被调用、调用后页表项有没有变化：

1. 用 `tools/lcfs.py` 从函数索引里挑出候选地址（按"被 `vm_fault` 调用的位置"筛）；
2. 在 fault 高峰期用 `HV_PCHK` 观察这个函数是否被执行；
3. 如果执行了但 PTE 仍为 0 ⇒ **写页表这一步本身有问题**（引擎实现或 guest 传参）；
4. 如果没执行 ⇒ 卡在 `vm_fault_enter` 之前的某个判断里（例如 mapping 状态不允许装入）。

## 4. 与之前所有结论的一致性

| 结论 | 状态 |
|---|---|
| entry 存在（登记没问题） | ✅ 多次确认 |
| PTE 不存在 | ✅ 多次确认 |
| 同一地址重复缺页 | ✅ 确认（`0x1007401cc` 出现两次） |
| 不是外部 abort（EA=0） | ✅ 确认 |
| 不是 TLB 写错页（mismatch=0） | ✅ 确认（40154 条 store） |
| 不是磁盘 I/O | ✅ 确认（ramdisk 在内存） |
| **故障横跨"匿名零填充"与"子映射"两条路径** | ✅ **本轮新增，指向 pmap 共同下游** |
