# GPU 阶段停住：两件独立的事

记录时间：2026-11-19 21:40 左右。对象：整机启动（非安装），8 核 / 3072 MB，reims-vgpu。

## 1. 观察到的现象

- UI 上进度条到 **50% 多**之后不再变化（与之前 CLI 的 49% 同一个位置）。
- `top -H`：`reims-vgpu.fifo` 线程 **100% CPU**，进程运行 797 秒时该线程已累计 **12 分 16 秒**。
- 日志（`vm/log/2026-11-19/HHMM.log`）每秒一行状态，全部是
  `帧缓冲=640x1136 | 模式=0 | guest 呈现=0 | host 呈现=0`，持续 6 分钟以上。
- 设备日志里 `command 0 of length 0, outside 12..=49152; skipped` 每毫秒几十条。

## 2. gdb 现场（进程 11973，root adb）

```
thread 4  (LWP 12125) "reims-vgpu.fifo"        100% CPU
threads 7-14 (8 个 guest CPU 线程)  全部 __futex_wait_ex → pthread_cond_clockwait
```

**没有崩溃，没有死锁，没有异常**。guest 的 8 个 CPU 线程全部停在条件变量上，即没有一处在执行
guest 代码。日志中唯一相关的事件是：

```
hengevm: wfi site #1 at pc fffffe001ca35e64 el1 daif 3c0
```

guest 执行 WFI 进入等待，之后没有任何中断把它叫醒。

**结论**：这一次不是"初始化慢"，是 guest 停在 WFI（idle），而 GPU 侧的线程在空转。

## 3. fifo 满负荷：ring 全 0，**未解决**，不加 sleep

`reims-vgpu-core/src/fifo/thread.rs`：

```rust
if command.length < HEADER_LEN || u64::from(command.length) > ring_length {
    // "Skipped without a stamp, a fault or an advance."
    return Framing::Skip;
}
...
Framing::Skip => continue,
```

`read` 不推进，`read_offset` 绕回去，于是反复重读同一个全 0 header —— 12 分 16 秒 CPU、0 条命令。
这一点是事实。

**但不加 sleep。** 曾经加过 500µs 又撤掉了，理由（操作者指出，且站得住）：

- GPU 的命令环本来就是**低延迟抢跑**，用等待换 CPU 占用等于拿响应速度换数字。
- 更重要的是，空转是**症状**：`command 0 of length 0` 说明 reims 读到的 ring 头部全是 0，
  而它认为 `written > read`（否则根本不会去读）。也就是 **guest 把 `written` 设成了非零，
  但 ring 里没有它写的命令** —— 这是 ring 映射或 `written`/`read` 语义不一致，
  加 sleep 对这个原因一点作用都没有。

**待查（下一步）**：

1. `HV_REIMS_LOG=1` 跑 CLI（`HV_BOOT_ONLY=1`），拿到 guest 写的 ring size / ring base 寄存器值
   （`reims: gfx write +0x1008 = ...`）。
2. 用同一个物理地址读 guest RAM，看 ring 的内容与 `written` 是否自洽：
   - ring 内容全 0 而 written 非 0 → guest 还没提交就报了 written，或 base 指错
   - ring 内容有命令而 reims 读不到 → 我们给的 memory map / 页视图有问题
3. 只有这两者之一被证实，才算找到原因。

## 4. 还没证明的事

- **为什么 guest 停在 WFI**：未定位。可能是它等的中断源（显示？定时器？）没有到来，也可能是
  8 核下的 SMP 唤醒问题。历史上有成功记录的是 **2 核**（CLI 跑到 ASR 90%）。
- **`模式=0` 是原因还是结果**：guest 没设显示模式，所以没有帧；但 guest 为什么不去设模式，
  与它停在 WFI 是同一个问题。

## 5. 下一次运行要拿的证据

新版本每次运行会打印，直接回答"在跑还是停住"：

```
显示页: cpu 5s 内变化=0 1 2 ...   | 0=0xfffffe001ca35e64(halt) 1=...
```

pc 在变 = guest 在工作；pc 不变 = 停在那个地址。这比 gdb 快，也不需要符号
（设备上的 `libhenge.so` 是 strip 过的 37 MB，gdb 只能看线程状态，看不见 `g_cpus`）。
