# 故障分布量化：不是单页，而是 6255 页里有一批反复装入失败（2026-11-17）

## 1. 数据

runS3（pid 22686，`workS3`）日志里共 16819 条 EL0 故障：

```
EC=0x24 data abort     15918
EC=0x20 instruction abort 901
```

按 16 KiB 页聚合：

| 指标 | 值 |
|---|---|
| fault FAR 覆盖的页 | **5920** |
| fault PC 覆盖的页 | **699** |
| 只 fault 1 次的页 | 1730 |
| fault 2 次的页 | 2141 |
| fault ≥5 次的页 | **667** |
| 单页最多 fault | **136**（`0x102614000`） |

## 2. 关键相关性：fault 次数多的页，至今仍未映射

在同一个地址空间（TTBR0=`0x600009a110000`）下逐一回查：

| 页 | fault 次数 | 回查结果 |
|---|---|---|
| `0x102614000` | 136 | **UNMAPPED**（desc=0） |
| `0x1002c0000` | 126 | **UNMAPPED** |
| `0x10030c000` | 123 | **UNMAPPED** |
| `0x1000f8000` | 119 | **UNMAPPED** |
| `0x101070000` | 91 | 已映射 `0xb4574000` |
| `0x1013a4000` | 8 | 已映射 `0xc7fec000` |

**fault 次数越多的页，越可能至今仍是空的。** 这是"反复装入失败"的直接证据，
而不是"某一页从未被访问"。

同时说明：绝大多数（约 5000 页）fault 1–2 次后就装好了 —— 那部分是**正常的按需装入**。
真正异常的是那 667 个反复失灵的页。

## 3. 这一轮排除掉的

| 假设 | 依据 |
|---|---|
| 单页问题 | 不是。6255 个页参与，667 个反复失败 |
| 引擎读错页表 | 排除。`hv_walk_dbg` 打印的 L1/L2 有效、L3=0，与手工遍历完全一致 |
| PTE 写了又被清（外部 abort） | 排除。ESR `EA=0`，不是 external abort |
| 等磁盘 I/O | 排除。ramdisk 在内存里，块设备无请求 |
| **PTE 写到错误的物理页**（TLB stale） | **排除**。`HV_SLOW_MEM=1` 下 `TLB-fresh mismatch` 计数为 **0**（共 40154 条 store 记录） |

## 4. 本轮发现的**工具盲区**（重要，先于结论）

两个方法问题，会影响后续所有判断：

1. **`ptw` 诊断按 4 KiB 匹配，而 guest 用 16 KiB granule。**
   `ptw_note()` 用 `page = pa & ~0xfff` 与记录的表页比较，`hv_ptw_sample()` 也只 diff 前 4 KiB。
   16 KiB 的 L3 表后三个 4 KiB 子页里的写入**完全看不到**。
   实测：出问题的 `0x100fc0000` 对应 L3 索引 999，字节偏移 7992 —— 落在第二个 4 KiB 子页，
   正是盲区。所以"用户范围写入 = 0"不能解释成"用户页表没被写"。

2. **`gdb` attach 期间被调试进程是暂停的。**
   在 attach 会话内做多次采样，看到的其实是同一冻结时刻 —— 之前"12 次采样完全一致"
   并不能证明"值不随时间变化"。

## 5. 因此下一步必须做成两件事之一

| 方案 | 代价 | 收益 |
|---|---|---|
| 让 `ptw` 诊断感知 granule（`page = pa & ~(granule-1)`，采样按 granule 大小做） | 小改动，属于**诊断工具**，不碰加载器 | 直接看到 16 KiB 表项到底有没有被写、写成什么 |
| 用"attach→读→detach→等→再 attach"的循环采样 | 零改动，但每轮 8 秒且会被下一轮覆盖 | 能看到值随时间变化，但抓不到瞬时状态 |

**建议先做第一件**：它是现有诊断的一个明确缺陷（4K 假设），修好之后
"PTE 有没有被写"这个问题会一次性有答案，而且对以后所有 16 KiB granule 的排查都有效。
