# 登记的"状态"：卡住页的 entry 与正常页**没有可见差异**

## 1. 先定 entry 的真实大小：0x50

用"相邻 entry 互相回指"来验证：

```
STUCK entry @ 0x8e33ba60
   +0x50 = 0xfffffe11260b5fd0   ← 正好等于 CODE entry 的 +0x00 (prev)
   +0x58 = 0xfffffe11260bfa60   ← 正好等于 CODE entry 的 +0x08 (next，即 STUCK 自己)
CODE  entry @ 0x8e33bab0 = 0x8e33ba60 + 0x50
```

**所以 `struct vm_map_entry` 在这台机器上是 0x50 字节**，有效字段只在 `+0x00..+0x4f`。
之前把 `+0x50` 之后的内容当成 entry 自己的字段，才误以为有"时间戳"。

## 2. 四种区间的字段对比（实测）

| 区间 | start | end | `+0x40`（object union） | `+0x48` |
|---|---|---|---|---|
| **卡住的页** | `0x100fc0000` | `0x100fc4000` | **0** | `0x2002b980` |
| 代码页 | `0x100f78000` | `0x100fc0000` | **0** | `0x2002bac0` |
| 低地址数据 | `0x100c84000` | `0x100cf4000` | **0** | `0x2002aac0` |
| 用户栈 | `0x16e980000` | `0x16f174000` | **`0x1e`** | `0x0002b800` |

`+0x40` 按 `vm_map_xnu.h` 的 union 解码：

```
0x0000001e = 0b11110
  vme_ctx_atomic     (:1) = 0
  vme_ctx_is_sub_map (:1) = 1      ← 栈是子映射
  vme_context       (:30) = 0x7
```

其余三个都是 0（`vme_kernel_object` 形态，非子映射）。

## 3. 这意味着什么

**卡住页的 entry 与代码页、数据页的登记状态，在这两个可见字段上完全一致**
（都是 `object_value = 0`，`+0x48` 只是对象/偏移打包值不同）。

也就是说：

- 它**不是** `is_sub_map`；
- 它**没有**任何"特殊标记"体现在 `+0x40`；
- 它的区间边界完全正常（正好一页，紧接在一个大区间之后）。

**结论：从登记的静态状态看，这一页与"正常但尚未装入"的页没有区别。**

这支持之前"page-in 未完成"的方向，而**不支持**"这是 guard/保留页、缺页本就该失败"的假设。

## 4. 还没定位的字段

`protection` / `max_protection` / `inheritance` / `vme_flags` 的位置**仍未确认**。

- 逐字节统计 1093 条 entry，唯一 99.5% 落在 1..7 的字节是 `+0x4a`，
  但它的值几乎恒为 `2`，而代码页（应 r-x）与栈（应 rw-）也同样是 `2`
  —— 所以它**不是**权限字段，只能是某个恒定标志位；
- 按开源布局推算的 `+0x50` 位域，实测是下一个 entry 的 `prev/next`（因为 entry 只有 0x50）。

**所以权限字段落在这 0x50 字节内的某处，且仅凭"值域 1..7"的统计无法定位**，
需要更强的手段（例如找一个已知 `PROT_NONE` 的 guard 区间做正对照，看哪个字段为 0）。

## 5. 下一步

1. **找一个 guard 区间做正对照**：XNU 在栈附近会放 `PROT_NONE` 的 guard page，
   从 map 里挑出紧邻栈的极小 entry，与卡住页对比逐字节差异，差异位即权限字段；
2. 或者用 `HV_PCHK` 观察 `vm_map_protect` / `vm_fault_enter` 在写这个 entry 时的 store 落点。
