# Android 界面规划（初稿）

> 状态：**初稿**。目标是先定职责边界，不追求完整。
> 原则只有一句：**一个界面只负责一件事**，宁可多一个入口，不要一个页面塞满。

---

## 一、五条硬约束（先定这些，再谈界面）

### 1. 引擎与 UI 分进程

```
:ui        Activity / Fragment / SurfaceView
:engine    libhenge.so + reims-vgpu + JIT + VM
```

理由：引擎里有 466k 行的 Rust 图形栈和自写 JIT。任何一次崩溃、OOM、看门狗都会
杀进程 —— 如果它和 UI 同进程，用户看到的是「闪退」；分进程，用户看到的是
「引擎异常退出，是否重启」，日志还在，状态还能救。

代价：跨进程通信。所以第二条。

### 2. UI 只发命令、只收快照

UI **永不**直接读引擎内部状态，引擎**永不**回调 UI 线程。

| 方向 | 形式 |
|---|---|
| UI → 引擎 | 命令队列（开始/暂停/停止/改配置/热插拔设备） |
| 引擎 → UI | 只读状态快照，按变化或定时（默认 500 ms）推 |
| 引擎 → UI | 帧：走 `Surface` 直接给渲染线程，不经 UI 线程 |

这条是从 `libadrenotools` 那次教训来的：跨层调用的参数约定错了，症状是静默失败。
所以边界要窄、要显式、要能测。

### 3. 显示面独立于所有 UI

`SurfaceView` 的 `Surface` 在 Activity 创建/销毁、旋转、分屏时都会变。
所以显示面不能和设置、日志住在同一个 Activity 里 —— 那些界面一刷新就重建显示面。

### 4. 不用 SDL 窗口

Android 的显示面由我们自己给：`SurfaceView` → `Surface` → `ANativeWindow`。
`reims-vgpu-window` 在 Linux 上走 SDL3，Android 这条路径要替换掉（技术上必须，
不是偏好）。

### 5. 每个 Activity 自己处理 inset

已实测的坑：`targetSdk 36` 下 Android 15 强制 edge-to-edge，不自己加
`WindowInsets` padding 就会被状态栏压住。**这不是显示页的问题，是所有页面**。

## 二、信息架构（一级）

```
┌─────────────────────────────────────────────────────────────┐
│  实例库  Library            ← 根页面                         │
│     ├── 实例详情 Instance   配置摘要 / 启动按钮              │
│     ├── 渲染 Renderer       驱动选择 / 后端 / 精度开关       │
│     ├── 存储 Storage        磁盘 / IPSW / 快照               │
│     └── 显示 Display        ★ 全屏，从「启动」进入           │
│                                                              │
│  诊断  Diagnostics          ← 抽屉                          │
│  日志  Logs                                                  │
│  设置  Settings                                              │
└─────────────────────────────────────────────────────────────┘
```

七个职责，七个去处：

| # | 界面 | 只负责 | 明确**不**负责 |
|---|---|---|---|
| 1 | **实例库** | 列出实例、创建、删除、显示配置摘要 | 不显示画面、不改驱动参数 |
| 2 | **实例详情** | 单个实例的配置（内存、CPU 核数、镜像路径、设备开关） | 不动全局设置 |
| 3 | **显示** | guest 画面、触摸/键鼠输入、最小覆盖层（返回、软键盘、性能浮层开关） | 不做任何配置修改 |
| 4 | **运行面板** | 实时指标（vCPU、JIT 命中率、内存、GPU、FPS）、暂停/恢复/重启、设备热插拔 | 不显示画面主体（浮层形式叠加在显示上） |
| 5 | **渲染** | 驱动来源（内置 Turnip / 系统 / 插件）、Vulkan 后端、分辨率、`REIMS_VGPU_EXACT` 精度开关 | 不改实例的 CPU/内存 |
| 6 | **诊断** | 现有探针：W^X 形状、Vulkan 能力、驱动来源、namespace 五步 | 不写日志文件、不改配置 |
| 7 | **日志** | 分级过滤、搜索、复制/导出/分享 | 不做实时指标图表 |
| 8 | **设置** | 全局偏好：语言、日志保留、默认驱动、默认精度档 | 不含单实例配置 |

### 两级导航

- **一级**：底部导航或抽屉 —— 实例库 / 诊断 / 日志 / 设置
- **显示**：不是一级页面，是「启动实例」后**推出**的全屏页，返回即停实例
- **运行面板**：显示页的浮层，不是独立页面（避免用户为了看 FPS 而离开画面）

## 三、显示页（唯一有 GPU 画面的页面）

### 构成

```
┌──────────────────────────────────────────────┐
│ [SurfaceView]                      ← 全屏    │
│                                              │
│   guest 画面（引擎直接渲染到 Surface）        │
│                                              │
│                              ┌─────────┐     │
│                              │ FPS 浮层 │     │  ← 可选，默认关
│                              └─────────┘     │
│  ┌────┐ ┌────┐ ┌────┐                        │
│  │返回│ │键盘│ │菜单│  ← 覆盖层，可自动隐藏  │
│  └────┘ └────┘ └────┘                        │
└──────────────────────────────────────────────┘
```

### 技术选择及理由

| 选择 | 理由 |
|---|---|
| `SurfaceView` 而非 `TextureView` | 独立合成层，guest 帧直接进 Surface，**零额外拷贝**；TextureView 要多一次 GPU 纹理拷贝 |
| 横屏 + `configChanges` | 旋转不重建 Surface，避免引擎侧的显示面抖动 |
| `FLAG_KEEP_SCREEN_ON` | 跑虚拟机时息屏等于挂起 |
| 触摸/键盘事件 → 命令队列 | 不直接调引擎，保持约束 2 |

### 与引擎的交接

```
SurfaceView.surfaceCreated(surface)
    → 把 Surface 通过 Binder 传给 :engine
    → 引擎侧 ANativeWindow_fromSurface() → VkSurfaceKHR
    → reims-vgpu 的 Presenter 往这个 surface 出帧
```

## 四、状态模型

一个实例的状态是**唯一真源**，UI 只读快照：

```kotlin
data class EngineSnapshot(
    val state: State,              // STOPPED / STARTING / RUNNING / PAUSED / FAILED
    val fps: Float?,
    val vcpu: List<CoreStat>,
    val memoryUsedMiB: Long,
    val gpu: GpuStat?,             // 驱动名、后端、扩展数
    val lastError: String?,
    val uptimeMs: Long,
)
```

UI 渲染只依赖快照，不依赖任何回调顺序 —— 这样进程重启、UI 重建都不会出现
「界面显示运行中但引擎已死」的状态不一致。

## 五、诊断页与日志页要分开

这两个容易混，但职责不同：

| | 诊断 Diagnostics | 日志 Logs |
|---|---|---|
| 内容 | **结构性事实**：W^X 授予哪种形状、Vulkan 扩展列表、驱动来源、namespace 哪一步失败 | **时间序列**：带时间戳的事件流 |
| 变化频率 | 一次运行一个结果 | 持续增长 |
| 用途 | 「这台机器能做什么」 | 「刚才发生了什么」 |
| 输出 | 一整份可复制报告 | 过滤后的片段 + 导出 |

现有的探针报告已经归入「诊断」，不动。

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **A** ✅ | 探针 | 已达成：W^X + Vulkan + 驱动来源 + namespace |

## 六之一、界面逻辑：对齐 Apple 那套

不是照抄外观，而是照抄**结构**，因为它解决的是同一类问题（一堆设置 + 一个流式日志 + 一份
机器报告）。三条规则：

| 规则 | 体现在 | 为什么 |
|---|---|---|
| **分组列表 + 行内显示当前值** | `Lists.group` / `Lists.row`：标题分组、行内 标题/副标题/当前值/› | 一屏读完状态，不用逐项点开；行是入口，不是表单 |
| **列表-详情（drill-down）** | 设置里每行点开设选择器或文本框；诊断里「原始报告」单独一层 | 列表保持可读，编辑集中在一次交互里 |
| **Console 式日志** | 搜索框 + 级别门槛（全部/信息+/警告+/仅错误）+ 自动滚底 | 日志是用来**缩小范围**的，不是从头读到尾 |
| **System Information 式诊断** | 报告按 `--- 分节 ---` 拆成分组，原始报告一键可取 | 「哪个驱动出的这些数」「namespace 哪一步失败」各自可定位 |

## 六之二、已实现（当前代码）

| 界面 | 文件 | 真实功能 | 占位部分 |
|---|---|---|---|
| 实例库 | `MainActivity` | 分组列表：虚拟机一行（名字 + `内存 · CPU · 驱动` + 状态 + ›）→ 显示页；管理组 → 设置/诊断/日志 | 只有一个实例；「新建」未做 |
| 显示 | `DisplayActivity` | 全屏 `SurfaceView`、surface 生命周期全部记日志、横屏 + `configChanges` + 保持常亮 | 引擎不跑 guest，画面是黑的，覆盖层写明原因 |
| 诊断 | `DiagnosticsActivity` | System Information 式：按分节渲染的分组报告 + 换驱动 + 重测 + 原始报告弹窗 + 复制/分享 | — |
| 日志 | `LogsActivity` | Console 式：搜索 + 级别门槛 + 实时追加 + 复制（复制的是筛选后的文本，所见即所复制） | 只覆盖本 app 自己的日志（Android 不允许读别的进程） |
| 设置 | `SettingsActivity` | 分组：实例（名称/内存/CPU，点开选择器或文本框）、渲染（全局驱动）、关于（诊断/日志/设备）；按名称持久化 | 改动在下次启动生效（运行中改内存等于崩溃） |

两个工程性约定：

- **JNI 入口集中在 `Native`**（`dev.henge.probe.Native.nativeProbe`）。搬动声明时 C 侧符号必须同步改名，否则是运行期 `UnsatisfiedLinkError` —— 已经踩过一次。
- **开发期四个界面在 manifest 里是 `exported="true"`**，便于 `adb shell am start` 直接抓某一页的日志；发布前必须收紧成 `false`，只在实例库里可达。

## 八、待定（需要后续决策）

1. **UI 技术栈**：现在是无依赖的 `Activity` + 手写 View。要不要引入 Compose？
   倾向：**先不引入**。显示页要极低开销，Compose 在长驻页面上不如 View 可控；
   等 C 阶段确认页面数量稳定后再评估。
2. **跨进程通道**：AIDL 还是 `AF_UNIX` + 自定义协议？倾向 AIDL（类型安全、
   系统托管生命周期），但帧通道必须另有专用路径，不走它。
3. **软键盘**：显示页需要文本输入时，是弹系统 IME 还是自绘键盘？倾向自绘
   （guest 的键盘布局和 Android 的不一定一致）。
4. **多实例并发**：允不允许同时跑两个？技术上 JIT + 4–8 GB RAM 让并发很勉强。
   倾向：**不允许**，第二个实例启动时提示先停掉第一个。
