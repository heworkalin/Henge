# 已知问题：GPU 只提交了"部分"更新（2026-11-21/22 记录，未修）

**一种故障，不是三种。** 观察者确认：画面会**随鼠标位置动态变好** —— 鼠标经过的区域会被
重新渲染成正确内容，其余区域保持旧内容。

于是三种外观都指向同一个机制：

| 外观 | 同一机制的成因 |
|---|---|
| 重复字形图块（"创建 Mac 账户"整屏 "H" 形图案） | 残留内容来自**上一个文字密集的帧**（字形图集），没被新帧覆盖 |
| 整屏竖条纹 | 残留内容 + 某处 stride/pitch 错位叠加 |
| 局部变黑 | 该区域被 clear 后**没有重绘** |

判据：**帧一直在到**（`guest presents` 持续增长），`PageFault`/`AccessRevoked` 为 0，
`gpu: 16%` —— 所以既不是"队列吊销→零帧"（那个已修，见 `docs/gpu-pixels-2026-11-21.md`），
也不是 GPU 算不动，而是**内容更新的范围错了**。

## 机制上的候选（按成本排序）

1. **脏矩形的坐标/尺寸用错**：guest 每帧只提交发生变化的 rect（PVG 的 present 参数里有
   offset/size），我们若整体当全屏更新，或把 rect 用了错的值/错了 stride，就只会小块正确。
2. **拷贝路径只覆盖了 rect 的一部分**：`copied` 在每次 completion 把 GPU 写过的字节合并回
   调用者的页；如果合并范围按"本次编码的 viewport"算，而 guest 的 rect 与之不一致，
   剩余区域就保持旧数据。
3. **IOSurface 的 dirty 列表**：guest 可能提交"若干 tile 已脏"；我们若只应用第一块。
4. **stride/pitch**：`display present ... 1920x1080 stride 15360`（= 1920×8），
   而 ARGB8888 应是 7680。若按 4 字节/像素解析，每行只取一半、整体错位。
5. **tiled/UBWC 未解**（最贵，前四条排除后再做）。

## 抓证据的顺序（不改代码就能区分）

| 想看什么 | 怎么做 |
|---|---|
| 是否"只有脏区域正确" | `HV_GRAB_EVERY` 连抓 `gpu-NNN.bmp`，**同时缓慢移动鼠标**：坏块是否随着鼠标路径被"补好" |
| 脏矩形的实际值 | 在 display present 处打印 rect（x/y/w/h）与 stride，和 mode 尺寸对比 |
| 合并回的范围 | `REIMS_DIAG=1` 看每次 completion 的 `offset/length`，与 rect 是否吻合 |
| 是 guest 侧还是我们侧 | 抓到的 BMP 也坏 = guest 画的就是坏 / 我们喂给 guest 的数据坏；抓到的正常而屏幕坏 = 上屏路径 |
