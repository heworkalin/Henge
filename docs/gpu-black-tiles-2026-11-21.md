# 已知问题：GPU 画面的竖条纹 / 内容错位（2026-11-21 记录，未修）

**现象**（操作者截图 `Screenshot_2026-11-21-23-44-03`，已 pull 到本地核对过）：

- 不是"局部黑块"。整屏是**规则竖条纹**：原本横排的文字被切成一条条竖带，
  每带的字形是同一批内容的**碎片**，带与带之间周期性重复；
- 内容"变了之后"更明显（重绘后整屏变成这种条纹），说明是**写入/读取的排布错**，
  不是随机花屏、也不是丢更新；
- 屏幕顶部 HUD 读数：`CPU 80% / GPU 6% / FPS 13.7`——即当前帧率只有 ~14fps，
  且瓶颈在 guest CPU（JIT），GPU 只占 6%。这与"画面投递很慢/像几秒前"的感觉一致。

## 形态判读

"竖条纹 + 周期性重复 + 内容碎片"是**行间距（pitch/stride）不匹配**的典型外观：
如果按错误的 stride 把一张图逐行搬运/采样，源图的每一行会被左移或右移固定量，
视觉上就是斜切/竖条纹，而不是颜色错。

佐证：设备上此前的 present 日志写着

```
display present #N: port 0 format 0x52476841 1920x1080 stride 15360
```

`15360 = 1920 × 8`，而 ARGB8888 应为 `1920 × 4 = 7680`。也就是说，guest 交上来的
surface **要么真是 8 字节/像素（两张图交错/两平面），要么 stride 字段的含义与我们的假设不同**。
我们按 4 字节/像素去解，就会出现"每行取一半、相邻行错位"的结果——与截图形态吻合。

## 待查（按顺序，成本从低到高）

1. **确认 stride 的真实含义**：在 present 处把 `stride / bpp` 与 surface 的 width 对比；
   若 `stride == width * 8`，检查是否两平面（例如 Y/CbCr 或 双缓冲交错）或 10bpc 打包。
2. **同一帧两条路对比**：`HV_GRAB_EVERY` 抓 `gpu-NNN.bmp`（我们解出来的帧）与
   `display present` 采样的像素，判断错位发生在**采样**（grab 也错）还是**上屏**（grab 对、屏幕错）。
3. **单矩形拷贝的 offset/length**：`REIMS_DIAG=1` 打开 `copied`/`host_memory` 探针，
   看每次 completion 的 `offset/length/stride` 是否符合 `width*4`。
4. **UBWC/tiled 的可能**：若 stride 与 8 字节/像素无关，而是 swizzle，则需要在导入时解 tile
   （Adreno 的 UBWC 格式）；这一条最贵，前面三条都能排除后再做。
