# 复盘：从"整机死锁"到"时间错了"（2026-11-19）

**一句话**：我们花了很长时间在缺页、锁、USB、显示、JIT 差异上找"内核为什么停住"，
最后发现根因只有一处——**guest 的计数器从宿主开机起算，导致时间漂到 2087、uptime 为负，
Apple 的个性化恢复材料因此不在有效期内，`restored_external` 停在第一个实质动作**。
修正 `counter()` 的基准后，恢复从 0% 推进到 ASR 90%。

本文记录：走对的、走过的偏路、判断错的地方、以及这次证实的"Apple 洁癖"。

---

## 1. 结论与证据

### 1.1 根因（实测）

```
core/sysreg.c: counter() = mach_absolute_time()          ← 宿主 CLOCK_MONOTONIC_RAW 缩放，从宿主开机起
实测 hv_counter()        = 12,778,900,511,786 ticks = 532,454 秒 = 6.16 天
宿主 /proc/uptime        = 552,498 秒（吻合）
guest commpage offset    = 0                              ← 内核 boot 时读到的基准是 0
→ guest 的 uptime = 宿主开机时长，restore-step-uptime 溢出成 -756316507015（约 -756 秒）
→ 串口时间戳 2087-06-30
```

### 1.2 修复与对照

只改 `counter()`：第一次调用时锁定基准，之后返回差值（guest 计数器从 0 开始）。

| 项 | 修复前 | 修复后 |
|---|---|---|
| `restore-step-uptime` | `-756316507015` | `8` |
| 串口时间戳 | 22:35 / 2087 | 16:08-GMT（= 宿主 UTC） |
| `set_progress_0`（0x0406） | **稳定卡住，无 END** | **通过** |
| 后续 checkpoint | 从未到达 | `update_fillmore` → `fdr_verify_sealed_manifest` → `commit_sep_os` → `await_system_image_invert_retry` |
| 系统镜像传输 | — | 11,733,565,440 bytes → `/mnt1/apfs_invert_asr_img` |
| **ASR 进度** | **0%** | **90%**（显示进度 54%） |

## 2. 走对的（可复用）

| 做法 | 为什么对 |
|---|---|
| **只改一个变量再对照**（`counter()` 的基准） | 修复前后行为差异只能归因于它 |
| **用 gdb 读运行中的实例，而不是反复重编重跑** | 一次 attach 就拿到 `hv_counter`、commpage offset、`g_board.rtc.offset`、设备树值 |
| **先看文档，不重走已排除的路** | `docs/exclusions-current-stall-2026-11-19.md` 的 43 项直接跳过 |
| **反编译上游 release IPA** | 不需要苹果设备就能确认上游构建事实（`adrp/add` vs GOT、没有 Q 保存、candidates 含 16/17） |
| **区分"实测"与"推断"** | 时间错→卡住是实测；"签名窗口拒绝"是推断，分开写 |
| **默认关闭所有实验性介入** | `HV_KFIX`、`HV_DT_LEN_PATCH`、`HENGE_RANDOM_SEED` 等默认关，避免掩盖真因 |
| **用独立测试包/自有测试程序验证** | 不碰用户设备上的第三方应用数据 |

## 3. 走过的偏路（按投入时间排序）

| # | 偏路 | 为什么走进去 | 最后怎么排除 |
|---|---|---|---|
| 1 | **缺页/PTE 未建立** | 早期确实观察到 PTE=0、同一地址重复缺页 | 后来证明 PTE 100% 建立，旧观测是**采样方式**问题；16 项全部排除 |
| 2 | **锁 / turnstile / 丢失唤醒** | 线程都在 WAIT，看起来像锁协议问题 | `thread+0x28` 读错（是 waitq 不是 turnstile）；`tsid=0`；`lck_mtx` 扫 18601 条命中 0 |
| 3 | **PV ticket lock** | 多核等待常怀疑这个 | 日志只有 3 条 OEM UID 调用，**没有一次 WFK/KICK** |
| 4 | **USB 链路** | restore 依赖 USB，且早期确实不通 | 后来 13161 请求 / 13161 响应完全配对 |
| 5 | **PCIe / 块设备 / 网络** | 都是 restore 路径上的设备 | ecam 正常、blk busy 0%、net 0/0 |
| 6 | **时钟频率（24 MHz 假设）** | 曾怀疑频率错 | 实测 23.9998 MHz 正确——**频率对，起点错**，这是最接近真相的一次偏路 |
| 7 | **kqueue / kevent_id** | 最后一条 syscall 是 kevent_id | 它只是 libdispatch 调度层；真正的等待是 `mach_msg2_trap` |
| 8 | **NVRAM 会话** | mach body 解出 `ramrod-nvram-session` | 方向对（Apple 恢复确实在等这个），但**不是因为 NVRAM 后端坏了**，而是签名/时间校验 |
| 9 | **显示 / PVG** | 公开日志里 `set_progress_0` 之后是 `found display` | 安装阶段只需要显示**设备模型**，不需要真渲染；`pvg_lite.c` 一直是完整的 |
| 10 | **JIT / 上游差异** | 与上游有 3 处语义差异 | 全部改掉后卡点仍在；上游 release 二进制也确认这些差异不是卡点 |
| 11 | **"整机累积死锁"** | 所有线程 WAIT、CPU 进 WFI、无 panic | **这个框架本身就是错的**：不是死锁，是"验证不通过所以停住"——看起来和死锁一模一样 |

**教训**：把"所有线程都停了"直接命名为"死锁"，会把排查引向调度/锁，
而真正的原因可能在**业务层的验证**上。名字会决定你往哪看。

## 4. 判断错的地方（"打的不对"）

### 4.1 结论层面的错误

| # | 错误的结论 | 实际情况 | 谁纠正的 |
|---|---|---|---|
| 1 | "日志里没有 X，所以没执行到 X" | **死锁/停住时日志链路本身不可信**，缺失是结果不是原因 | 用户纠正 |
| 2 | "设备 CLI 能验证显示" | CLI 编的是 `pvg_metal_stub.c`，且没有窗口/Surface 权限 | 用户纠正 |
| 3 | "SIMD 不保存是上游 bug（D-3）" | 只能证明"我们的构建需要"；上游 0.3 二进制确认它不保存且能跑 → 降级 U-10 | 用户纠正 |
| 4 | "D-1/D-2 是上游错误" | 机制是架构级的，但**没有解释上游为什么能跑**；解释不了就不能判 D | 用户纠正 |
| 5 | "时间修好了，卡点没变" | **只看 25 秒**；`set_progress_0` 只是还没到继续的那一刻 | 用户指出"他真的开始工作了" |
| 6 | "PTE 恒为 0" | 采样方式问题（chaining 下的取样点） | 后续实测 |
| 7 | "turnstile 的 proprietor 是 +0x50" | 结构偏移读错（那是 waitq）；结论作废 | 后续 type 自证 |
| 8 | "USB 读了但没传回" | 三个闸门的推断成立，但它不是卡点原因 | 时间修复后流程继续 |

### 4.2 介入层面的错误（代码/补丁）

| # | 介入 | 问题 | 现在 |
|---|---|---|---|
| 1 | `HV_KFIX`（内核 rebase） | 一度被当成必修，实际内核自己会 rebase，补一次会**多加一次 slide** | 默认关 |
| 2 | `HV_DT_LEN_PATCH`（设备树长度改成 16 MB） | 让内核走过真实树尾 | 默认关 |
| 3 | `HENGE_RANDOM_SEED` | 每次运行 physmap slide 不同，实验不可复现 | 默认关 |
| 4 | 一批 opt-in 介入掩盖 `__PRELINK_TEXT` 0 块 | `d272f3a` 全部默认关后才看到真相 | 已关 |
| 5 | `HV_SLOW_MEM` 曾在内核启动时自动打开 | 把 guest 拖到每秒千块 | 改为 opt-in |
| 6 | 安装模式链接 reims-vgpu | `memory.map.mapping_length_unaligned` → `death::die` → abort | **已改为安装模式走 `pvg_lite`** |

**教训**：**"先补一个试试"是弯路的主要来源。** 每个介入都要能回答"如果它是对的，
现象应该怎么变"，并且默认关闭、可对照。

## 5. 这次证实的"Apple 洁癖"

Apple 对时间/签名的要求比一般系统严格得多，**不能用 Linux 的直觉处理**：

| 层 | Apple | Linux 常见情况 |
|---|---|---|
| TSS 个性化 | 票据带签发/有效期窗口，按 ECID 生成 | 无此机制 |
| 证书链 | 有效期校验，过期即拒绝 | 通常只影响 TLS |
| APTicket / nonce | 与时间、ECID、nonce 绑定 | 无 |
| `restore-outcome` 等状态 | 带时间戳，参与后续判断 | 无 |
| **时间偏差的后果** | **验证不通过，流程停在第一个实质动作** | 通常只影响日志与超时 |

**实测证据**：只改 `counter()` 的基准，`restored_external` 从"永远停在 `set_progress_0`"
变成"推进到 ASR 90%"。没有改任何签名、证书、恢复栈代码。

**推论（未直接观测）**：时间错 → TSS/证书时间窗口判断失败 → 个性化材料不被认可 → 停住。
这条要保持"推断"标签，直到真的读到校验器的拒绝记录。

## 7. 一句话总结

> **不是内核死锁，是时间错了；不是锁、不是 USB、不是显示、不是 JIT。**
> Apple 的恢复流程把时间当作验证前提，时间偏 60 年，它就不往下走。
> 修好时间后，同一套代码、同一份镜像，直接跑到 ASR 90%。
>
> 弯路的价值在于它把 43 项排除了；代价是**没有一个早期动作去核对"guest 看到的时间"**。
> 以后任何 Apple 恢复相关的问题，**时间正确性应当是第一个检查项**，而不是最后一项。
